SLIDE 10 — PIPELINE (~1 min 30s)
============================================================

"Le pipeline GitHub Actions comporte 4 jobs.

Job 1 : build et tests de l'API .NET. Il setup .NET 9,
restore, build en Release, et exécute les tests xUnit.

Job 2 : lint et build du frontend React.
npm ci avec --ignore-scripts pour la sécurité supply chain,
puis ESLint et le build Vite.

Job 3 : scan de sécurité avec Trivy — il détecte les CVE
CRITICAL et HIGH sur les dépendances .NET.

Job 4 : analyse SonarCloud — qualité de code statique,
avec un Quality Gate bloquant.

Le pipeline se déclenche sur tous les push et PR
vers develop et master."


============================================================
SLIDE 11 — SÉCURITÉ DU PIPELINE (~1 min)
============================================================

"J'ai appliqué plusieurs mesures de sécurité dans le pipeline lui-même.

Les actions GitHub tierces sont épinglées sur leur hash SHA complet,
pas sur un tag mutable comme @v4. Ça protège contre les supply chain attacks
— si quelqu'un compromise l'action upstream, mon CI continue d'utiliser
la version que j'ai validée.

npm ci avec --ignore-scripts empêche l'exécution de scripts
arbitraires lors de l'installation des dépendances.

Les tokens — SONAR_TOKEN, JWT_KEY — sont passés via des variables
d'environnement et non interpolés directement dans les commandes,
pour éviter qu'ils apparaissent dans les logs.

Un déploiement en production nécessite que les 4 jobs soient verts
ET une approbation manuelle via GitHub Environments.
C'est le verrou de déploiement."

SLIDE 15 — OWASP TOP 10 (~1 min 30s)
============================================================

"J'ai analysé les 10 vulnérabilités de l'OWASP Top 10
et calculé un score de criticité pour chacune.

Les principales :

A01 Broken Access Control — score 6, le plus critique.
Couvert : JWT avec RBAC, tous les endpoints sensibles
sont décorés [Authorize(Roles='ADMIN')].

A03 Injection SQL — couvert par Entity Framework Core
qui génère exclusivement des requêtes paramétrées.
Zéro SQL brut dans le code.

A07 Authentication Failures — partiel. J'ai sécurisé le JWT,
mais le rate limiting sur le login et la politique
de complexité de mot de passe sont planifiés.

A05 Security Misconfiguration — partiel. Le CORS est actuellement
AllowAnyOrigin en développement. En production, il faut
le restreindre à l'URL Railway uniquement — c'est planifié."


============================================================
SLIDE 16 — ACTIONS CORRECTIVES (~1 min)
============================================================

"Concrètement, ce qui est implémenté :

JWT RBAC sur tous les endpoints sensibles.
La clé JWT est sortie du code source — elle est dans les secrets.
EF Core pour toutes les requêtes — zéro injection possible.
Trivy dans le CI pour détecter les composants vulnérables.
SHA pinning sur les actions GitHub tierces.

Ce qui est planifié : rate limiting sur le login,
restriction CORS, et complexité de mot de passe.

Au total, j'ai couvert 90% des risques identifiés
sur les 9 risques applicables — A10 ne s'applique pas
car CESIZen ne fait aucun appel vers des ressources externes."

SLIDE 18 — DONNÉES (~1 min)

"CESIZen collecte trois types de données.

Des données classiques : email et mot de passe — le mot de passe

SLIDE 20 — SCÉNARIOS (~1 min)
============================================================

"J'ai documenté 4 scénarios de crise avec des niveaux de priorité.

P1 — critique : fuite de données. Réponse : isolation du service
sur Railway, rotation immédiate des credentials,
et notification CNIL dans les 72 heures — obligation légale RGPD.

P1 — compromise du pipeline CI/CD : désactivation immédiate,
reset de tous les secrets, audit des commits récents.

P2 — indisponibilité : vérification du statut Railway,
rollback sur la version stable précédente.

P3 — intrusion détectée : analyse des logs, ticket security GitHub,
hotfix via une branche dédiée.

RTO à 2 heures, RPO à 24 heures.
Chaque incident donne lieu à un post-mortem documenté
dans GitHub Issues."

RÉPONSES PRÉPARÉES AUX QUESTIONS PROBABLES
============================================================

Q : Pourquoi pas Docker ?
R : "J'ai évalué Docker. Pour un projet solo, Railway couvre exactement
le besoin : build auto, TLS, variables isolées, rollback rapide.
Docker apporterait de la portabilité — utile si on change d'hébergeur
ou si on ajoute des services comme Redis. C'est prévu en v2."

Q : C'est quoi le STRIDE ?
R : "STRIDE est une méthode de modélisation des menaces développée par Microsoft.
Chaque lettre correspond à un type d'attaque : Spoofing (usurpation d'identité),
Tampering (modification de données), Repudiation (nier une action),
Information Disclosure (fuite), Denial of Service, Elevation of Privilege.
J'ai analysé 28 menaces sur 5 composants, avec 3 cycles de révision."

Q : Différence test unitaire / fonctionnel ?
R : "Un test unitaire vérifie une logique isolée — par exemple,
que le score 149 est bien classifié 'Faible' et pas 'Modéré'.
Un test fonctionnel vérifie un comportement bout en bout —
par exemple, POST /login avec des bons credentials retourne bien un token JWT.
Les deux sont complémentaires."

Q : Le SIEM c'est quoi exactement ?
R : "SIEM signifie Security Information and Event Management.
Dans mon cas, c'est un workflow GitHub Actions qui s'exécute
toutes les 15 minutes, ping l'API de production,
et crée ou ferme des tickets GitHub en fonction de la réponse.
C'est une version simplifiée mais fonctionnelle des systèmes
de monitoring utilisés en entreprise."

Q : La réinitialisation de mot de passe ?
R : "Ce que j'ai implémenté, c'est le changement de mot de passe —
l'utilisateur doit connaître son ancien mot de passe.
La vraie réinitialisation par email nécessiterait un service SMTP
ou une intégration SendGrid. C'est documenté comme perspective d'évolution
dans les milestones GitHub — v2.0.0."

Q : Tu as utilisé de l'IA pour ce projet ?
R : "Oui, j'ai utilisé Claude comme outil d'assistance.
Il m'a aidé à structurer des analyses (OWASP, STRIDE),
à déboguer des configurations CI/CD, et à rédiger certaines documentations.
Mais toutes les décisions techniques sont les miennes :
le choix de Railway, l'architecture JWT, la structure du pipeline.
L'IA est un outil de productivité, comme un linter ou un moteur de recherche.
Ce qui compte c'est que je comprends et que je peux expliquer
chaque choix — et c'est ce que je fais aujourd'hui."
