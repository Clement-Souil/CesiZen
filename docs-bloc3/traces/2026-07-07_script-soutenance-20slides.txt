SLIDE 4 — ARCHITECTURE & FONCTIONNALITÉS (1 min 30 s)
═══════════════════════════════════════════════════════════════════════════════
"CESIZen est une application full-stack.
Côté backend : une API REST en .NET 9 ASP.NET Core, MySQL 8 via Entity
Framework Core, et une authentification JWT avec roles USER et ADMIN.
Côté frontend : une web app React 18 + TypeScript + Vite, et une application
mobile React Native + Expo.
L'ensemble est déployé sur Railway, un PaaS cloud.

Trois modules fonctionnels :
— Module 1 : Comptes utilisateurs, inscription, connexion, RBAC complet.
— Module 2 : Ressources documentaires avec filtres et approbation admin.
— Module au choix : Diagnostics de stress Holmes & Rahe, 43 événements
  pondérés scientifiquement, calcul de score, interprétation et historique."

SLIDE 6 — VERSIONING & ENVIRONNEMENTS (1 min 15 s)
═══════════════════════════════════════════════════════════════════════════════
"Pour le versioning, j'utilise Git Flow adapté sur GitHub.
Deux branches protégées : master pour la production, develop pour
l'intégration. Aucun commit direct n'est autorisé — tout passe par Pull Request
avec CI obligatoirement verte.
Convention de commits : feat:, fix:, ci:, security: pour la traçabilité.

Pour les environnements :
— Développement en local avec dotnet run, npm run dev et WampServer.
— CI/Test sur GitHub Actions ubuntu-latest : build, tests, lint, scan.
— Production sur Railway avec déploiement automatique au merge sur master.
— Le rollback est possible en moins de 2 minutes via le dashboard Railway.
— Les secrets sont gérés en trois couches : appsettings en dev,
  GitHub Secrets en CI, Variables Railway en prod."

SLIDE 8 — PIPELINE CI.YML (1 min 10 s)
═══════════════════════════════════════════════════════════════════════════════
"Le pipeline GitHub Actions ci.yml comporte 5 jobs automatisés, déclenchés
à chaque push et pull request sur develop et master.

Job 1 : Build et tests de l'API — setup .NET 9, restore, build Release, xUnit.
Job 2 : Lint et build du frontend — npm ci, ESLint, Vite build.
Job 3 : Scan de sécurité Trivy — deux scans CVE CRITICAL et HIGH, un sur les
dépendances NuGet du backend, un sur les dépendances npm du frontend.
Job 4 : SonarCloud — analyse statique et Quality Gate bloquant.
Job 5 : Deploy Gate — approbation manuelle via GitHub Environments avant tout
déploiement en production, même pour moi.

Aucun code défaillant ne peut atteindre la production."

SLIDE 9 — SÉCURITÉ DU PIPELINE (1 min)
═══════════════════════════════════════════════════════════════════════════════
"J'ai sécurisé le pipeline lui-même contre les attaques supply chain.
Les actions tierces GitHub sont épinglées sur leur SHA complet — pas sur
une version tag qui peut être modifiée.
npm ci s'exécute avec --ignore-scripts pour neutraliser les scripts malveillants.
Les secrets — SONAR_TOKEN, JWT_KEY — passent par des variables d'environnement,
jamais dans le YAML en clair.
SonarCloud surveille la qualité et la sécurité du code en continu — l'analyse
se fait uniquement via la CI, pas en double avec l'analyse automatique de
SonarCloud, pour éviter les conflits de configuration."

SLIDE 20 — MERCI (30 s + Q&R)
═══════════════════════════════════════════════════════════════════════════════
"Je vous remercie pour votre attention.
Je suis disponible pour vos questions."

─── Si on me demande sur l'IA ───────────────────────────────────────────────
"J'ai utilisé Claude Code comme assistant de développement, similaire à
GitHub Copilot mais avec plus d'autonomie. Je reste l'auteur de toutes
les décisions techniques : choix d'architecture, analyse OWASP, politique
RGPD. L'IA m'a aidé à aller plus vite sur l'implémentation, ce qui m'a
permis de consacrer plus de temps à la sécurité et à la documentation."

─── Si on me demande sur le reset de mot de passe ───────────────────────────
"J'ai implémenté le changement de mot de passe — qui nécessite l'ancien
mot de passe. La réinitialisation par email avec token temporaire est
identifiée comme axe d'évolution v2 : elle implique un service SMTP et une
table de tokens à durée limitée."

─── Si on me demande sur Railway vs Docker ──────────────────────────────────
"Railway offre CI/CD automatique, HTTPS, et base de données managée
sans configuration Docker ni infra à gérer. Pour un projet individuel
étudiant, c'est le meilleur rapport complexité/valeur. Docker reste
pertinent pour des déploiements plus complexes ou on-premise."

─── Si on me demande sur STRIDE ──────────────────────────────────────────────
"STRIDE est un framework de modélisation des menaces : Spoofing, Tampering,
Repudiation, Information Disclosure, Denial of Service, Elevation of Privilege.
J'ai utilisé OWASP Top 10 comme référentiel principal car plus adapté
aux applications web, mais STRIDE est complémentaire pour l'analyse
des flux de données."

─── Si on me demande comment je sais que mes "conteneurs" sont sécurisés ────
"Nuance importante : je n'ai pas de Dockerfile — Railway construit le
conteneur automatiquement via Railpack. Trivy scanne donc mes dépendances
en mode fs, pas une image construite en mode image. C'est un compromis du
choix PaaS : simplicité contre contrôle direct sur l'image. Je n'utilise pas
Snyk non plus — Trivy fait déjà ce travail de SCA, sur le backend et le
frontend, sans ajouter un outil et un compte supplémentaires."

─── Si on me demande le fonctionnement exact du JWT et du RBAC ─────────────
"À la connexion, l'API vérifie le mot de passe haché BCrypt, puis génère un
JWT signé HMAC-SHA512 contenant l'identifiant, l'email et le rôle, valide
1 heure. Chaque endpoint sensible porte un attribut Authorize avec le rôle
requis — ASP.NET Core vérifie ça côté serveur à chaque requête, impossible
à contourner depuis le frontend. Le mot SHA a deux sens différents dans le
projet : HMAC-SHA512 pour signer le JWT, et le SHA d'un commit Git pour
épingler les actions GitHub tierces contre les attaques supply chain."
